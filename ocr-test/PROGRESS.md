# 온통청년 공고 PDF 파싱 — 진행 상황

작성: 2026-10-06 · 위치: `ocr-test/`

## 1. 목표

온통청년 정책 데이터(API)를 기본으로 쓰고, API에 없거나 비어 있는 정보를 **첨부 공고 PDF**에서 보충해 에이전트가 쓸 데이터로 만든다.
제약: **LLM·토큰 사용 없음**(로컬 LLM도 불가) → 규칙(정규식) + 좌표 기반 처리만 사용.

## 2. 현재 구조

```
온통청년 API ─► samples/policies.json   정책 3,153건 (60개 컬럼, 기본값 겸 정답지)
      │
collect.py ──► samples/*.pdf            공고 PDF 100개 + manifest*.jsonl (정책별 첨부·건너뜀 사유·수집일)
      │
ocr.py  parse()   PDF → 페이지별 텍스트
      │   ├ 글자 있는 페이지 → PyMuPDF (기호 변환·띄어쓰기 복원)
      │   ├ 글자 없는/깨진 페이지 → PaddleOCR (별도 프로세스, 시간 제한)
      │   ├ 표 → find_tables (병합셀 채움·가짜 표 제거·쪽 넘김 표 머리글 연결)
      │   └ 나머지 → group() 좌표 기준 묶기
      │
extract.py   규칙 추출. 값마다 {value, status, reason, evidence, page}
      │       신청기간(시작·종료·구분), 나이(최소·최대), 지원인원, 지원금액(원 단위)+주기
      │
merge.py ───► samples/merged.jsonl      API + PDF 병합, 필드별 상태(정상/확인필요/충돌/없음)·출처·근거
      │
evaluate.py  규칙 결과 vs API 채점 (20개 묶음 단위)
viewer.py    브라우저 뷰어 (localhost:8765) — PDF 위에 줄·묶음·표 박스 표시
codes.json   공통코드표 11개 그룹 + 시군구 256개
```

환경: Python 3.13 가상환경(`.venv`), `requirements.txt` = pymupdf 1.28.2 / paddlepaddle **3.2.2(고정)** / paddleocr 3.7.0. API 키는 `.env`(git 제외).

## 3. 진행 순서와 결과

| 단계 | 내용 | 결과 |
|---|---|---|
| 1 | API 응답 확인 | 이미 JSON 구조화 데이터. PDF는 첨부파일에만 있음 |
| 2 | PyMuPDF + PaddleOCR 설치·테스트 | 한국어 OCR 동작 확인 |
| 3 | 첫 실제 PDF(포스터, 이미지형) | 54줄 인식, 0.9 이상 33줄 |
| 4 | 뷰어 제작 | 줄/묶음/표 박스 시각화 |
| 5 | 좌표 묶기(위아래 줄 문제) | 포스터 카드 12쌍 모두 짝 맞춤 |
| 6 | 텍스트형 공고 4개 | 표 깨짐 발견 → find_tables 도입 |
| 7 | 공고 9개 규칙 추출 vs API | 30개 항목 중 25개 정답(83%) |
| 8 | 코드표 확보 | 사이트 공통코드 API + 시도/시군구 API |
| 9 | 공고 100개 수집·채점(20개×5묶음) | 아래 표 |
| 10 | 예외처리 전면 수정 | 4장 참고, **재채점 진행 중** |

### 100개 채점 결과 (예외처리 수정 전)

| 컬럼 | 규칙 | 기준선(항상 최빈값) | **값을 냈을 때 정답률** |
|---|---|---|---|
| 신청 시작/종료일 | 45% / 46% | 6% / 7% | **94% / 97%** |
| 최소/최대 나이 | 44% / 63% | 48% / 57% | **97% / 91%** |
| 지원인원 | 24% | 10% | **92%** |
| 코드 칸(취업·학력·특화 등) | 23~97% | 41~98% | — (기준선보다 나빠서 **API 값 사용**으로 결정) |

결론:
- 규칙이 **값을 냈을 때는 91~97% 정답** → "API 우선, 빈칸만 PDF로 보충, 못 찾으면 비움" 구조로 감.
- 신청기간을 못 채운 19건 중 13건은 PDF에 날짜 자체가 없음(상시·예산소진형 등) → 날짜 대신 **신청 구분(상시/예산소진/공고일부터)**을 저장하도록 변경.
- 코드 칸은 API 값의 80~98%가 "제한없음"이라 키워드 규칙이 오히려 손해.

## 4. 막혔다가 해결한 문제

| # | 문제 | 원인 | 해결 |
|---|---|---|---|
| 1 | PaddleOCR 실행 시 `NotImplementedError` | paddlepaddle 3.3의 Windows CPU oneDNN 버그 | 처음엔 `enable_mkldnn=False`로 회피 |
| 2 | OCR 한 장에 85~180초 | 1번 회피로 CPU 가속이 꺼짐 + **옵션을 안 넣으면 기본값이 꺼짐** | paddlepaddle **3.2.2로 고정** + `enable_mkldnn=True` 명시 → 약 20~30초(6배 빠름) |
| 3 | 200dpi 이상에서 세그폴트 | 큰 이미지 검출 단계 문제 | 검출 입력 긴 변 1280px 제한 |
| 4 | 뷰어가 OCR 중 응답 없음 | 단일 스레드 서버 | ThreadingHTTPServer + OCR은 Lock으로 직렬화 |
| 5 | 포스터 제목·카드가 줄 단위로 쪼개짐 | OCR은 줄 단위 결과 | 좌표 겹침·간격 기준으로 묶기(`group`) |
| 6 | 표 값이 섞임(행 이름보다 숫자가 먼저) | 좌표 묶기는 표 구조를 모름 | PyMuPDF `find_tables`로 셀 구조 추출 |
| 7 | 좁은 화면에서 표 숫자 잘림 | CSS `word-break:break-all` | 셀은 `keep-all` + 가로 스크롤 |
| 8 | PDF 다운로드가 401 | 세션 쿠키·사전 확인 요청 필요 | 홈 접속(쿠키) → `atchFileDetInfoCheck` → 다운로드 |
| 9 | 공개 API에 첨부 정보 없음 | `atchFileMngSn`은 사이트 내부 API에만 있음 | `/wrk/yrm/plcyInfo/plcy/{정책번호}` 사용 |
| 10 | 수집 속도(정책 258건에 PDF 7개) | 파일명 포함 조건이 너무 좁음 | 포함 조건 제거, 제외 목록(신청서·포스터·책자 등)만 사용 |
| 11 | 수집이 1시간 이상 걸림 | 요청을 순서대로 하나씩 | 작업자 4개 병렬(정책 번갈아 분담) → 수십 분 |
| 12 | 작업 중지 후에도 수집이 계속됨 | 백그라운드 중지가 python 자식 프로세스를 못 죽임 | PID로 직접 종료, 이후 PID 파일 기록 |
| 13 | 처리 시간이 24~180초로 들쭉날쭉 | **원인 미확인**(발열·전원관리 추정) | 해결 못 함 |
| 14 | 지역코드 정확도 15% | 코드표 시도명은 "전남광주통합특별시", 공고문은 "광주" | 시도 별칭표 추가 → 30% |
| 15 | API "마감" 규칙이 오히려 정확도 하락 | API의 마감 표시가 날짜 기준으로 갱신 안 됨 | 규칙 제거, 마감 여부는 `merge.py`에서 오늘 날짜로 직접 계산 |
| 16 | 기호가 `q`·`m`으로 나옴 | HWP→PDF 공고의 Wingdings 글꼴 | 글꼴 이름 보고 변환표로 □·○ 등으로 바꿈 |
| 17 | 양쪽 정렬 문단 띄어쓰기 사라짐 | PDF에 공백 문자가 없음 | 글자 좌표 간격으로 공백 복원 |
| 18 | 해 넘김 기간(12.1~1.31)의 종료일이 시작일보다 앞 | 종료일 연도 생략 시 시작 연도 사용 | 역전되면 다음 해로 보고 `확인필요` |
| 19 | 없는 날짜(2월 30일) 그대로 저장 | 날짜 검증 없음 | 검증 후 `확인필요` |
| 20 | "만 19세 이상 39세 이하" → 0~39세 | `~` 없는 범위 패턴 미지원 | 패턴 추가 |
| 21 | 선정순위·제외대상 문장의 나이를 자격으로 잡음 | 문서 전체에서 첫 번째 값 사용 | 자격 줄 우선, 순위·우대·제외 줄 무시, 한쪽 표현은 자격 줄에서만 |
| 22 | 출생연도 범위·예외조건(군필자) 미지원 | 패턴 없음 | 출생연도 → 나이 근사(`확인필요`), 괄호 예외는 사유로 기록 |
| 23 | 정책 하나의 네트워크 오류로 수집 전체 중단 | 재시도 3회 후 예외가 그대로 올라감 | 정책 단위로 실패 기록 후 계속, 다음 실행 때 재시도 |
| 24 | 정책당 PDF 1개만 받음 | 의도적 제한 | 전부 받음, 같은 문서는 연결만 기록 |
| 25 | OCR 세그폴트가 뷰어·일괄처리 프로세스까지 죽임 | 세그폴트는 Python에서 못 잡음 | OCR을 별도 프로세스로 실행 + 시간 제한 |
| 26 | 깨진·암호 PDF 처리 없음 | — | `ParseError`로 문서만 건너뜀, 페이지 오류는 페이지만 표시 |
| 27 | 스캔본의 엉터리 텍스트층을 그대로 믿음 | 텍스트가 있으면 무조건 사용 | 정상 글자 비율 60% 미만이면 OCR로 대체 |
| 28 | 병합 셀이 빈칸 / 가짜 표 / 쪽 넘김 표 머리글 없음 | find_tables 기본 동작 | 가로·세로 병합 채움, 빈 칸 비율로 가짜 표 제거, 앞 쪽 머리글 연결 |

## 5. 확인된 데이터 특성 (API 쪽)

- 신청기간이 빈 정책이 많음(100개 중 33개).
- 연령제한 "없음"인데 나이 값이 있는 경우, 하한 1세 같은 이상값 존재.
- 대상이 명확히 미취업자인데 취업조건 "제한없음" 등 코드 값 일관성 낮음.
- 종료일이 지나도 "마감"으로 바뀌지 않음.
- 첨부 PDF 100개 중 지난해 공고 의심 5건, 수정·정정 공고 10건, 이미지 페이지 포함 9건.

## 6. 진행 중 / 남은 일

- [진행 중] 예외처리 수정 후 100개 재파싱·재채점, `merge.py` 첫 실행.
- 단락 나누기(질의응답용): 지원내용·신청방법·제출서류 등을 제목 기준으로 잘라 저장.
- 추가 칸: 소득기준(중위소득 %), 문의처(전화번호), 신청 장소·URL.
- 에이전트 용도(추천형 / 질의응답형) 결정 필요.

## 7. 검증하지 못한 부분

- 4장 16~28번 수정은 **자체 검사(가짜 입력)와 일부 실제 문서로만 확인**. 100개 전체 영향은 재채점 결과로 확인 예정.
- 암호 PDF·엉터리 텍스트층 처리는 실제 사례가 100개에 없어 가짜 입력으로만 검증.
- "지난 공고 의심"은 문서 앞부분 연도 비교 추정이며 원문은 열어보지 않음.
- API 오답 중 API 쪽 오류 비율은 세지 않음.
- 처리 시간 편차(13번) 원인 미확인.
